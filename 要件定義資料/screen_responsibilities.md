# niwa.log 画面責務定義書

> 各画面の「何を表示して」「何を操作できて」「どこに遷移するか」を定義する。
> ペルソナシート・遷移図と合わせてGPTへの設計資料として使用する。
> レイアウト・ビジュアルの判断はGPT/Figma側に委ねる。ここでは情報と機能の定義に徹する。

---

## 1. ダッシュボード

アプリの中核画面。ログイン後の起点であり、日常動線の9割がここで完結する。

### 1-1. ファーストビュー（メインコンテンツ）

**植物一覧 × 水やりスコア**

- 登録済みの全個体を一覧表示
- 各個体に最低限表示する情報：
  - ニックネーム（「ラベンダー3号」等）
  - 水やりスコア（あげるべき度）
  - 品種名
- デフォルトのソート順：スコアの高い順（＝水やりが必要な子から）
- スコアが低い個体も非表示にせず一覧に残す（えりちゃんペルソナ：「あげなくていい」を確認する行為自体に価値がある）

### 1-2. 補助情報

- 今日の天気（スコアに影響している要因の可視化。判断の安心材料）
- 庭名・地域名

### 1-3. 操作できること

| 操作               | 動作                             | 備考                                         |
| ------------------ | -------------------------------- | -------------------------------------------- |
| 「あげたよ」ボタン | 水やりログをワンアクションで記録 | ダッシュボード上で完結。個別詳細への遷移不要 |
| 植物をタップ       | 個別植物詳細へ遷移               | ステータス確認・メモ・品種情報を見たいとき   |
| 植物追加           | 植物登録モーダルを表示           | 新しい個体を登録                             |

### 1-4. 遷移先

- → 個別植物詳細
- → 水やりログ記録（ワンアクション。画面遷移ではなくダッシュボード上で完結）
- → 植物登録モーダル

### 1-5. 設計上のポイント

- 日常動線の中心。「開く→確認→あげる/あげない→閉じる」が最短で完結する設計
- えりちゃんペルソナ：スコアが低い子を見て「今日はあげなくていい」と安心できる
- 30代奥さんペルソナ：スコアが高い子だけ見て水やり→5分で完了
- 「あげたよ」のワンアクション記録が鍵。個別詳細を経由させない

## 2. 個別植物詳細

ダッシュボードから「もっと知りたい・確認したい」ときに遷移する画面。

### 2-1. 表示内容

- ニックネーム、品種名
- 水やりスコア（現在値）
- ゾーン（庭のどのエリアにいるか）
- 個体メモ（「最近元気ない」等の観察記録）
- 水やり履歴（直近のログ一覧）
- 品種の基礎知識への外部リンク（育て方・特性など外部サイトへ誘導）
- タグ（品種名「ブルースピア」、管理メモ「挿し木組」等）

### 2-2. 操作できること

| 操作               | 動作                             | 備考                                           |
| ------------------ | -------------------------------- | ---------------------------------------------- |
| メモ追加・編集     | 個体の観察記録を更新             |                                                |
| 「あげたよ」ボタン | 水やりログ記録                   | ここからも記録可能（ダッシュボードと同じ機能） |
| 個体情報の編集     | ニックネーム・ゾーン・タグの変更 |                                                |
| 個体の削除         | 個体を庭から削除                 | 確認ダイアログ必須                             |

### 2-3. 遷移先

- ← ダッシュボードへ戻る
- → 外部サイト（品種の基礎知識）

---

## 3. ユーザー登録 ステップ1（ユーザー情報 + 庭）

初回フローの入口。ユーザー情報と庭の基本情報をまとめて取得する（A案確定）。

### 3-1. 入力項目

- メールアドレス
- パスワード（+ 確認入力）
- 表示名
- 庭の名前（「うちの庭」等）
- 地域（サジェスト選択 → regions への upsert）

### 3-2. 遷移先

- → 登録ステップ2（植物登録）

### 3-3. 設計上のポイント

- v1は1ユーザー1庭なので、庭の作成を独立した意識にさせない
- 地域はサジェストから選択。手入力ではなく候補から選ぶUX
- 入力項目は最小限。プラン種別等は初回登録では取らない

---

## 4. ユーザー登録 ステップ2（植物登録）

初回セットアップの仕上げ。スキップ可能。

### 4-1. 表示内容・操作

- 植物マスタからのサジェスト検索（名前の前方一致）
- マスタから選んで個体を登録（ニックネーム・ゾーンは任意）
- 複数個体の連続登録が可能
- 「あとで追加する」でスキップ → ダッシュボードへ

### 4-2. 遷移先

- → ダッシュボード（登録完了 or スキップ）
- → 植物マスタ登録（サジェストに該当なしの場合）

### 4-3. 設計上のポイント

- 「最低1つ登録してね」ではなく「スキップOK」を明示。初回のだるさを最小化
- ここで登録すると、ダッシュボードに着いたとき空っぽではない状態を作れる

---

## 5. 植物登録モーダル

ダッシュボードから呼び出す。日常的に植物を追加するときの導線。

### 5-1. 表示内容・操作

- 植物マスタからのサジェスト検索
- 個体情報の入力（ニックネーム・ゾーン・メモ・タグ、いずれも任意）
- 登録完了 → モーダルを閉じてダッシュボードに反映

### 5-2. 遷移先

- ← ダッシュボード（閉じる）
- → 植物マスタ登録ページ（マスタに該当なしの場合）

### 5-3. 設計上のポイント

- モーダル表示。画面遷移ではなくダッシュボードの文脈を維持
- 登録ステップ2とUI/コンポーネントを共通化できる余地あり

---

## 6. 植物マスタ登録

植物マスタに未登録の品種を新規投稿する画面。

### 6-1. 表示内容・操作

- 植物名の入力
- 親カテゴリの選択（既存マスタからサジェスト。なければ親として新規登録）
- 水やり基本係数の入力（目安情報として）
- 投稿 → 承認待ちステータスで保存

### 6-2. 遷移先

- ← 植物登録モーダル or 登録ステップ2 に戻る

### 6-3. 設計上のポイント

- 投稿後は即座にマスタとして使えるわけではない（モデレーター承認制）
- 当面シングルユーザー＝自分がモデレーターでもあるので、実運用上は即承認可能
- 2階層制約：親を選んだ場合、その親がすでに子であればエラー

---

## 7. TOP

アプリの入口。LP的な役割。

### 7-1. 表示内容

- アプリの概要・特徴（hero セクション）
- ユーザー登録への導線
- ログインへの導線

### 7-2. 遷移先

- → ユーザー登録（ステップ1）
- → ログイン

### 7-3. 設計上のポイント

- 初期は最小限でOK。hero + CTA（登録ボタン）程度
- 将来的にスクリーンショットやユーザーの声を追加する余地を残す

---

## 8. ログイン

### 8-1. 入力項目

- メールアドレス
- パスワード
- 「ログイン状態を保持する」チェック（リメンバートークン、30日TTL）

### 8-2. 遷移先

- → ダッシュボード（認証成功時）
- → パスワードリセット（将来実装）

### 8-3. 設計上のポイント

- 定型的な構成でOK
- パスワードリセットはv1では後回し可

---

## 9. FAQ / 利用規約 / お問い合わせ

フッターからの共通導線。

### 9-1. 共通方針

- FAQ と利用規約は UI を共通化（工数削減）
- データソースは JSON で十分（DB不要）
- 初期状態では必要最小限の内容で公開し、あとから育てる

### 9-2. お問い合わせ

- フォーム形式（名前・メール・内容）
- 送信先はメール通知で十分（v1では管理画面不要）
