## 2. 主要な設計判断（v0.2で確定したこと）

### 2-1. 位置情報は「座標」をやめて「地域」で持つ **[v0.2変更]**

v0.1 では gardens に座標（緯度経度）を持ち、プライバシー防御（丸め・viewer非公開・DAO層でSELECT除外）に気を遣う設計だった。
v0.2 では **庭は座標を持たず、地域マスタ（regions）への参照を持つ**方針に変更。

効果：
- 居住地特定リスクが構造的に下がる（庭が持つのは「地域」止まり、ピンポイント座標を保存しない）
- v0.1 のプライバシー防御の大半（座標の丸め・DAO層除外など）が不要になり設計が簡素化
- viewer向け天気粒度の4段階制御は「必須の防御」から「任意の表示設定」へ格下げ可

### 2-2. 地域サジェストは外部サービス任せ、地域マスタはオンデマンドで育てる **[v0.2新設]**

- **候補出し（サジェスト）は外部API**が担当（全国の地名を自前で全件保有しない）
  - サジェスト用APIの候補：HeartRails Geo API / 国土地理院系など（日本特化・無料）
  - 天気取得用API：OpenWeatherMap（座標 or city_id）
  - ※サジェスト用と天気取得用は別APIでよい。サジェストが返す座標を天気取得に流用する
- **ユーザーが候補を選んだ時点で、regions に1行 upsert**（無ければ作成・有れば再利用）
- 同じ地域を別ユーザーが選んでも新規作成せず既存行を共有 → weather_cache を地域単位で共有できる
- 結果：使われた地域だけ regions に蓄積されていく。将来データが育てば自前地域DBとして独立可能

**二重作成の防止が要件**：外部APIが返す安定した地域識別子（city_id / 地域コード等）を
regions のユニークキーにする。表記揺れで同一地域が複数行できると天気キャッシュ共有が崩れるため必須。

### 2-3. シーズン状態は enum で持つ **[v0.2変更]**

- CSVサンプルでは `シーズン状態: Float` になっていたが、これは誤り
- 仕様上は「アクティブ / 休眠」の状態切替なので **enum（`active` / `dormant`）** で持つ
- 将来的に移行期を入れたければ `transition` を足せる余地を残す
- Float（連続値で休眠度合いを持つ）という解釈は意図と異なるため不採用

### 2-4. moderator はグローバルロール、user_roles に混ぜない **[v0.2整理]**

- owner / viewer / contributor は「特定の庭に対する権限」→ user_roles（庭単位）で管理
- moderator は「植物マスタの承認権限」で、特定の庭に紐づかない**全体権限**
- これを庭単位の user_roles に混ぜると設計が歪むため、**moderator は別管理**
  - 案：users に `is_moderator` フラグ / または専用テーブル
  - 当面シングルユーザーなのでフラグで十分、必要に応じ拡張

## 3. テーブル別 項目定義

### 3-1. users（ユーザー）

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| email | ログイン用 | ユニーク |
| password_hash | ハッシュ化して保存 | 平文保存禁止 |
| display_name | 画面上の名前 | |
| plan | free / premium | 拡張用フラグ |
| is_moderator | モデレーター権限フラグ | **[v0.2]** グローバル権限 |
| created_at | アカウント作成日 | TIMESTAMP（tz付き推奨） |

### 3-2. gardens（庭）

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| owner_id | どのユーザーの庭か | users 参照 |
| name | 「うちの庭」等 | |
| region_id | どの地域か | **[v0.2]** regions 参照（旧・座標を置換） |
| season_state | active / dormant | **[v0.2]** enum（旧 Float） |
| created_at | 庭の作成日 | TIMESTAMP |

- 初期は1ユーザー1庭、課金解放で複数庭対応想定

### 3-3. regions（地域マスタ）**[v0.2 新設]**

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| external_id | 外部API由来の安定した地域識別子 | **ユニーク**。二重作成防止キー |
| name | 地域名（表示用） | プルダウン/選択結果の文字列 |
| lat | 代表座標（緯度） | 天気API用。ユーザー非公開の内部値 |
| lng | 代表座標（経度） | 同上 |
| created_at | この地域がDBに作られた日 | |

- 全件事前投入はしない。ユーザーが地域を選んだ時に upsert で育てる
- 粒度は市区町村レベルを目安（天気は正確に引け、特定リスクは低い）

### 3-4. zones（ゾーン）

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| garden_id | どの庭のゾーンか | gardens 参照 |
| name | エリア名 | |

### 3-5. plants（植物マスタ）

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| name | 「イングリッシュラベンダー」等 | サジェスト対象。**インデックス必須** |
| parent_id | 親カテゴリのID | NULL = 親カテゴリ自身。自己参照 |
| water_coefficient | 種別ごとの水分要求度 | スコアリング用 |
| approval_status | draft / approved / rejected | モデレーターが管理 |
| submitted_by | 誰が追加したか | users 参照 |

設計上の注意（Code に判断委ねず方針を明示）：
- **2階層固定**。自己参照FKは技術的に無限階層を許すので、
  「parent_id を持つ行（＝子）はさらに子を持てない」をアプリ側 or DB制約で担保する
- 承認ステータスは親子それぞれが持つ。子が未承認・親が承認済のときのサジェスト表示挙動は要決定
  （当面：承認済のみサジェストに出す、で十分）
- サジェストは `name` への前方一致（`LIKE 'xxx%'`）。`name` に B-tree インデックス1本で足りる
- 部分一致や表記揺れ吸収（pg_trgm / 正規化カラム）は件数増加後の拡張ポイント。初期は不要

### 3-8. watering_logs（水やりログ）

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| user_plant_id | どの個体にあげたか | user_plants 参照 |
| watered_at | 水やりした日時 | TIMESTAMP |
| memo | 任意メモ | 「葉がしおれ気味」等 |

- 「あげた」のみ記録。「あげなかった」は記録しない（記録なし=あげてない）
- 降雨との棲み分け：行動記録はここ、雨が降った事実は weather_cache（自動・地域単位）
- スコアリング時に両方を統合
- 検討メモ：降雨補正を後から正確に振り返りたい場合、ログに当時の天気参照を持たせる案あり。初期は必須でない

### 3-9. weather_cache（天気キャッシュ）**[v0.2 キー変更]**

| 項目 | 内容 | 備考 |
| --- | --- | --- |
| id | 通し番号 | 自動採番 |
| region_id | どの地域の天気か | **[v0.2]** regions 参照（旧・庭単位） |
| observed_at | 取得時刻 | |
| condition | 天気大分類（晴/曇/雨/雪） | |
| temp / humidity 等 | 詳細データ | owner向け表示・スコアリング用 |

- 地域単位でキャッシュ。同じ地域の複数の庭で共有 → API呼び出し・保存を節約（無料枠に優しい）
- ポーリング頻度はシーズン状態で変動（アクティブ期：1〜2時間ごと / 休眠期：1日1回）

### 3-10. user_roles（権限）

| ロール | 権限 | スコープ | 導入時期 |
| --- | --- | --- | --- |
| owner | 全操作（CRUD・設定・招待） | 庭単位 | v1 |
| viewer | 読み取り専用 | 庭単位 | v2 |
| contributor | 水やりログ追加 | 庭単位 | 将来 |
| moderator | 植物マスタ承認 | **グローバル**（users.is_moderator） | v1〜 |

- user_roles テーブルが扱うのは庭単位ロール（owner/viewer/contributor）
- 同一 (user, garden) に複数ロールが入らないよう複合ユニーク制約
  - contributor と viewer を同時に持つケースを許すかは要決定（当面は単一ロールで可）
- moderator は user_roles に入れず、users のフラグで管理（2-4参照）

## 4. Code に渡す前に残っている小さな決め事

優先度高（スキーマが分岐するので先に決める）：
1. ~~シーズン状態の型~~ → enum で確定
2. ~~座標の持ち方~~ → 地域マスタ参照で確定
3. ~~moderator のスコープ~~ → グローバル（usersフラグ）で確定

優先度中（方針が決まれば Code が普通に書ける）：
- regions の external_id に使う外部APIの確定（サジェスト用APIの選定）
- 植物マスタ 2階層制約を「アプリ側」か「DB制約」どちらで担保するか
- (user, garden) に複数ロールを許すか（contributor + viewer 併存の可否）

優先度低（後から足せる拡張ポイント）：
- 植物サジェストの部分一致・表記揺れ対応（pg_trgm / 正規化カラム）
- 水やりログへの天気参照付与（降雨補正の振り返り精度向上）
