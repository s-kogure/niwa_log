## 2026-09-17 Phase5-7 認証・認可ミドルウェア方針（決定事項）

### 検討の背景

Phase5-7として、Express側の認証・認可ミドルウェアを設計するにあたり、
先に「JWTの検証方式」と「RLSとバックエンドDB接続の橋渡し方法」を決めておく必要があった。
この2つが決まらないと、ミドルウェアの実装方針（`req.user`に何を積むか、DBクエリの前後で何をするか）が固まらないため。

### 発見事項：現状のRLSはバックエンドから見て機能していない

`.env.example`の`POSTGRES_USER=postgres`は、migrationを実行したテーブルオーナー＝スーパーユーザーである。

PostgreSQLの仕様上、RLSはテーブルオーナー・スーパーユーザーには適用されない
（`FORCE ROW LEVEL SECURITY`を明示しない限り）。migrationにもこの指定はない。

つまり現状のバックエンド接続（固定の`postgres`ロールで`pg.Pool`）からは、
`docs/db_settings/RLS.md`で設計した23本のPolicyが実質すべてスルーされる状態になっている。
この点は方針に関わらず必ず修正が必要。

### 検討した選択肢

**論点1：RLSの`auth.uid()`とバックエンドDB接続の橋渡し**

- (a) リクエスト（トランザクション）ごとに`SET LOCAL`でJWTクレーム相当をPostgreSQLセッション変数へ流し込み、RLSをPostgRESTと同様の形で機能させる
- (b) RLSは保険として有効にしたまま、実際の所有者チェックはExpress側＋SQLのWHERE句で明示的に行う
- (c) `pg`直結をやめ、PostgREST／`supabase-js`経由のデータアクセスに全面移行する

**論点2：JWT検証方式**

- `jsonwebtoken`でのローカル検証（Supabase JWT secretを使用）
- `supabase-js`の`auth.getUser()`によるSupabase Auth側への検証委譲

### 決定事項

- **JWT検証**：`supabase-js`の`auth.getUser()`に委譲する
- **RLS連携**：(a)方式を採用する。あわせて、バックエンドのDB接続ロールを`postgres`（スーパーユーザー）から、権限を絞った`authenticated`相当の専用ロールに切り替える
- **(c)への全面移行は今回見送り**

### 決定理由

開発者本人（ユーザー）が「セキュリティ面は素人なので、安全側に倒したい」という前提があった。
これを踏まえて検討した結果、以下の理由でSupabaseの標準的な仕組みに寄せる方向を選んだ。

- `jsonwebtoken`によるローカル検証は正しく実装すれば問題ないが、alg confusion等の実装ミスの余地が自分の手元に残る。`supabase-js`側の検証に委譲することで、その実装リスクをSupabase側の実装に肩代わりしてもらえる
- (b)は「所有者チェックを毎回SQLのWHERE句に手書きする」設計であり、書き漏らしのリスクが本人の実装力に直結する
- (a)は、`docs/db_settings/RLS.md`で既に設計・レビュー済み（`claude_codeレビュー.md`／`codexレビュー.md`）の23本のPolicyをそのまま活かせる。これはSupabase本来の仕組み（PostgRESTがJWTクレームをセッション変数に流し込んでRLSを機能させる仕組み）を自前で再現するアプローチであり、"Supabaseに寄せる"という方針とも合致する
- (c)は`pg`直結をやめる全面的なアーキテクチャ変更となり、Phase5-3「DB接続共通化」で確定・検証済みの接続方式を作り直すことになるため、今回のスコープとしては大きすぎると判断した

### 追記（同日）：DB接続分離の詳細設計

上記の「RLS連携」決定を実現するにあたり、DB接続まわりをさらに詰めた。

**発見事項：migrationも同じ`pool`を共有している**

`backend/db/migrate.js`は`backend/src/db.js`の`pool`（＝単一の`POSTGRES_USER`接続）をそのまま使っている。
migrationは`CREATE TABLE`／`ENABLE ROW LEVEL SECURITY`／`CREATE POLICY`／`GRANT`を要するため、
権限を絞った専用ロールでは実行できない。よって単純に`POSTGRES_USER`を差し替えるだけでは済まず、
**DB接続を2系統に分離する**必要がある。

- migration用：既存の`postgres`（スーパーユーザー）のまま。`migrate.js`はこの接続を単独で保持する
- アプリ実行時用：新規に権限を絞った専用ログインロールを作成し、`db.js`のpoolをこちらへ切り替える

**決定：新規ロール名は`authenticator`**

`db_init/001_stub_auth.sql`が既に`anon`／`authenticated`／`service_role`というSupabase／PostgREST本家の用語をそのまま使っている。
これに合わせ、「ログインしてJWTクレームをセットしてから`SET ROLE`で切り替える」役割のロール名は、
PostgREST公式が定めるこの役割の呼称である`authenticator`をそのまま採用する（プロジェクト名プレフィックスは付けない）。

- `authenticator`は`LOGIN` / `NOINHERIT`とし、`authenticated`ロールのみを`GRANT`する
- `NOINHERIT`にすることで、`SET ROLE authenticated`を忘れた場合にRLSがバイパスされるのではなく、
  単に権限不足（`permission denied`）で弾かれるfail-closedな挙動にする
- `service_role`（植物マスタ承認・天気キャッシュ更新等の運営処理用）は、現状`005_grant_table_privileges.sql`側にも権限が振られておらず未着手。今回のスコープ外として保留する

**決定：env var名**

`POSTGRES_USER`／`POSTGRES_PASSWORD`は公式postgres Dockerイメージ自体のブートストラップ変数（コンテナ初期化時のスーパーユーザー作成に使われる）であり、アプリ用途に転用すべきではない。そのため新規に以下を追加する。

```
AUTHENTICATOR_USER=authenticator
AUTHENTICATOR_PASSWORD=...
```

`POSTGRES_USER`／`POSTGRES_PASSWORD`はmigration用としてそのまま維持する。

**決定：db_initでのロール作成は`.sh`スクリプトにする**

`docker-entrypoint-initdb.d/`は`.sql`だけでなく`.sh`（シェルスクリプト）も実行可能。
`docker-compose.yml`の`db`サービスは`env_file: .env`により`.env`の内容がコンテナの環境変数として渡るため、
`.sh`スクリプト内で`$AUTHENTICATOR_PASSWORD`を読み取って`psql`に渡す形にする。
これにより、パスワードをgit管理下のSQLファイルへ直書きすることを避ける。

## 2026-09-17 Phase5-7 DB接続分離 実装

上記の決定事項・詳細設計に基づき、以下を実装した。

- `.env.example`／`.env`：`AUTHENTICATOR_USER`/`AUTHENTICATOR_PASSWORD`を追加
- `backend/src/config.js`：`db`（`authenticator`ロール、アプリ実行時用）と`migrationDb`（`postgres`スーパーユーザー、migration専用）を分離してexport
- `backend/db/migrate.js`：`src/db.js`のpool共有をやめ、`config.migrationDb`を使う独自の`pg.Pool`を保持するよう変更
- `backend/db/db_init/002_create_authenticator.sh`：`authenticator`ロール（`LOGIN` / `NOINHERIT`）を作成し、`authenticated`ロールへ`GRANT`するスクリプトを追加

ローカルDBボリュームを作り直し（`docker compose down -v` → `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d`）、`npm run migrate`でmigrationを再実行した上で、psqlで以下を実地検証した。

| 検証 | 結果 |
|---|---|
| `authenticator`でログイン | 成功 |
| `SET ROLE`せずに`users`をSELECT | `permission denied`（`NOINHERIT`によるfail-closedが機能） |
| `SET ROLE authenticated`後に`users`をSELECT | 0件（エラーではない＝GRANTは通過し、RLS Policyが機能している） |

これにより、「発見事項：現状のRLSはバックエンドから見て機能していない」で挙げた問題を解消した。既存の23本のRLS Policyが、DBレイヤーとしては意図通り機能する状態になったことを確認済み。
