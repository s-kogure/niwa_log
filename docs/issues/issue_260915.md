Phase5-6として、Express共通エラーハンドリングを整備するにあたり、
着手順とエラーレスポンスのフォーマットを先に決めた。

### 実装順（合意事項）

エラーレスポンスの形式が決まっていないと後続がすべて手戻りになるため、
以下の順で進める。

1. エラーレスポンスのフォーマット統一

3. 404ハンドラ（2の仕組みに乗せて共通ハンドラに渡す）
4. 共通エラーハンドリングミドルウェア（app.jsの一番下に配置する受け皿本体）

### エラーレスポンスフォーマット（仮設計）

ネスト構造＋バリデーション等の複数エラーをまとめられる`details`を持つ形とする。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください",
    "details": [
      { "field": "name", "message": "植物名は必須です" }
    ]
  }
}
```

- トップレベルのエラーは基本的に1個（`error`直下）。
- 複数フィールドにまたがるバリデーションエラー等、まとめて返したい場合のみ`details`配列を使う。
- 単純なエラー（404、DB接続エラー等）では`details`を省略してよい。

検討した他パターン（不採用）：

- フラット単一エラー（`{ code, message }`のみ）：複数バリデーションエラーを一度に返せず、往復が増えるため不採用。
- JSON:APIスタイル（常に`errors`配列でトップレベルを包む）：単純なエラーまで配列に包むのは過剰と判断し不採用。

### `code`（アプリ独自エラーコード）について

アプリ独自の`code`（文字列）を持たせる方針とする。

- メリット：HTTPステータスだけでは区別できない意味の違いをフロントで判別できる、ログ集計がしやすい、後方互換を保ちやすい。
- デメリット：列挙の管理コストが増える、フロント・バックエンドでの文字列同期がずれるとtypoでバグる。

個人開発かつ学習目的であることを踏まえ、最初から全列挙を作り込まず、
今使う分だけ（`VALIDATION_ERROR`, `NOT_FOUND`, `UNAUTHORIZED`, `FORBIDDEN`, `INTERNAL_ERROR`程度）
から始めて、必要になったら追加する運用とする。

### 開発者向け情報の扱い

現状の開発者は本人とAIのみのため、レスポンスの型に開発者向けフィールドを常設はしない。

- サーバー側ログ（`console.error`等）には元のエラー（スタックトレース含む）を出す。
- クライアントへのレスポンスには、`NODE_ENV === 'development'`の時だけ
  `stack`等の追加情報を載せる分岐を入れる（本番では絶対に出さない）。
